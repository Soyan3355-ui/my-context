## 0. この基準書の読み方

### 0.1 目的

この基準書は、次の三つを同時に防ぐための「社内規程」である。

1. **暴走** — エージェントが任された範囲を越えて、的外れな方向へ勝手に進むこと
2. **監督過多** — 人間がすべてを確認し、効率が上がらないこと
3. **空回り** — 会議・報告・資料が増えるだけで、売上・顧客・納品物などの事業成果につながらないこと

三つの原因は共通している。**完了と成功の判定が、エージェントの内側（自己申告、互いの合意、自分で編集できる指標）にあること**である。本基準は、その判定を外側（独立した検収、外部証拠、人間が管理するKPI）に移すことを中心に組み立てている。

### 0.2 規範の強さ

| 表記 | 意味 |
|---|---|
| **必須** | 例外なく守る。技術的に強制できるものは権限・フック・CIで強制する |
| **推奨** | 原則として守る。外れる場合は設計メモに理由を書く |
| **任意** | 状況に応じて採用する |

各ルールには、根拠の強さを `[強]` `[中]` `[推論]` で付記する。

- `[強]` 複数の公式ガイド・標準・研究が一致している
- `[中]` 限定的な実験、特定用途、一社の報告に基づく
- `[推論]` 根拠から導いた設計判断、または初期値。運用データで調整する

### 0.3 改訂のルール

- この基準書、`kpi/`、`acceptance/`、`.claude/settings*.json`、`.claude/hooks/` の変更は、**エージェントによる提案 → オーナーの承認（PRのマージ）** の経路でのみ行う（`GOV-02`）。
- 版数は `MAJOR.MINOR.PATCH` とする。原則の追加・削除はMAJOR、ルールの追加・閾値の変更はMINOR、表現の修正・出典の更新はPATCHとする。
- 変更履歴は `standards/CHANGELOG.md` に記録する。
- 週次リサーチ（第14章）で新しい知見が出たら、この基準書への改訂提案として扱う。

## 1. 基本原則（10則）

| ID | 原則 | 強さ |
|---|---|---|
| `PRI-01` | **単純な構成から始める。** まず単一エージェント＋タスクボード＋完了定義で回す。複数エージェントは第2章の条件を満たすときだけ使う。 | 必須 `[強]` |
| `PRI-02` | **成果物を書く担当は常に1体。** 調査役と検収役は読み取り専用にする。 | 必須 `[強]` |
| `PRI-03` | **作成と承認を兼務させない。** 成果物を作ったエージェントに、その合否を判定させない。 | 必須 `[強]` |
| `PRI-04` | **役割ではなく必要な文脈で分ける。** 「企画係→文章係→校正係」のようなリレーにしない。 | 推奨 `[中]` |
| `PRI-05` | **状態は会話ではなくファイルに置く。** タスクボード、進捗ログ、決定記録を正とする。 | 必須 `[強]` |
| `PRI-06` | **自己申告の「完了」は無効。** 完了は外部証拠と独立した検収で判定する。 | 必須 `[強]` |
| `PRI-07` | **採点する側とされる側を分ける。** KPI、受入基準、設定、フックはエージェントが編集できない場所に置く。 | 必須 `[強]` |
| `PRI-08` | **会議は議論ではなく決定の手続き。** 独立起案 → 採点・投票 → 決定記録で終える。 | 必須 `[中]` |
| `PRI-09` | **禁止事項はプロンプトではなく仕組みで止める。** CLAUDE.mdは助言、権限・サンドボックス・フック・CIが強制層である。 | 必須 `[強]` |
| `PRI-10` | **人間には例外だけを届ける。** 人間の関与は「意図の承認」「不可逆・対外・金銭の承認」「例外の裁定」の3点に絞る。 | 必須 `[強]` |

一文にまとめると、次のとおりである。

> **自律的に作業させ、機械的に検査し、独立に反証させ、高影響の境界だけ人間が承認する。そして完了は事業成果に結びつけて判定する。**

## 2. 構成の選択基準

| ID | ルール | 強さ |
|---|---|---|
| `ARC-01` | 新しい仕組みを作るときは、次の表の上から順に検討し、最初に要件を満たすものを採用する。 | 必須 `[強]` |
| `ARC-02` | 複数エージェントを使ってよいのは、(a) 相互依存の少ない作業が2つ以上ある、(b) 一つの文脈に収まらない大量の調査がある、(c) 独立した検証の価値が高い、のいずれかを満たし、かつ追加コスト（単一の3〜15倍のトークン）を上回る便益を説明できる場合に限る。 | 必須 `[強]` |
| `ARC-03` | 同じファイル・同じ決定を複数のエージェントに共同所有させない。並列で書く必要がある場合は `isolation: worktree` とファイル所有権を明示する。 | 必須 `[強]` |
| `ARC-04` | 役職を模した階層（社長・部長・課長…）や「CEOエージェント」は作らない。管理機能は手順・道具・チェックリストで実現する。 | 必須 `[中]` |
| `ARC-05` | Agent Teams（実験的機能）は、サブエージェントでは実現しにくい直接協調のユースケースに限り、隔離した試験として使う。定型業務や本番の意思決定には使わない。 | 必須 `[中]` |

| 構成 | 向いている仕事 | 避ける条件 | 扱い |
|---|---|---|---|
| 単一エージェント＋ツール | 小さく明確、低リスク、短時間 | 多角的な調査、巨大な文脈 | **既定** |
| 固定ワークフロー（スキル・定期実行） | 手順が安定し、検査できる反復業務 | 手順自体を探す必要がある | **量産の第一選択** |
| 司令塔＋サブエージェント | 分解が必要な調査、複数領域 | 密な逐次依存、同一ファイルの編集 | 条件付き標準 |
| 独立並列＋検収役 | 見落としのコストが高い、複数仮説の比較 | 正解の基準がまったくない | 高価値用途 |
| Agent Teams | エージェント間の直接対話に真の価値がある | 定型業務、同一資源の競合 | 実験枠 |
| 自由討論・スウォーム | 研究目的 | 実運用の意思決定、対外行為 | **不採用** |

## 3. 役割の標準

### 3.1 標準5役（＋任意1役）

| ID | 役割 | 実体 | 責任 | 書き込み範囲 | モデル目安 |
|---|---|---|---|---|---|
| `ROL-00` | **オーナー（人間）** | 人間 | 目的・優先順位・KPI・完了定義の決定、不可逆行為の承認、月次の成果レビュー | すべて | ― |
| `ROL-01` | **司令塔** `chief-of-staff` | メインセッション | 計画案の作成、タスク分解と委任、ボード更新、成果物の統合、オーナー向けダイジェスト | `tasks/` `workspace/` `decisions/` `progress.md` | opus |
| `ROL-02` | **調査役** `researcher` | サブエージェント（並列可） | 一次情報の収集、出典つきの要約 | なし（結果を返すだけ） | sonnet / haiku |
| `ROL-03` | **制作担当** `producer` | サブエージェント（同時に1体） | 下書き・台本・告知文・資料・コードの作成 | `workspace/drafts/` など指定範囲のみ | sonnet / opus |
| `ROL-04` | **検収役** `reviewer` | サブエージェント（新しい文脈） | 受入基準に照らした合否判定と証拠確認。反証を試みる | なし | opus |
| `ROL-05` | **成果分析役** `outcome-analyst` | サブエージェント（週次・月次） | KPI実績とタスクの対応づけ、赤信号の検出 | `reports/metrics/` のみ | sonnet |
| `ROL-06` | **リスク担当** `security-reviewer`（任意） | サブエージェント（条件付き招集） | 機密情報・認証・決済・本番・外部送信・権限変更を含む場合のみ審査 | なし | opus |

- `ROL-10`（必須 `[強]`）: 他のエージェントを呼び出せるのは司令塔だけとする（`tools: Agent(...)` で制限する）。
- `ROL-11`（必須 `[中]`）: 司令塔は調査役・検収役の出力を**要約し直さずにそのまま**ファイルへ保存してから使う（伝言ゲームの防止）。
- `ROL-12`（推奨 `[推論]`）: 役割を追加するのは、既存の役割で3回以上同じ種類の仕事が詰まったときだけとする。追加時は第13章のチェックリストを通す。
- `ROL-13`（推奨 `[推論]`）: 高価なモデルは司令塔、曖昧な判断、最終検収に集中させる。ただし、コスト削減のために検収の能力を下げない。

### 3.2 責任分担（RACI）

| 活動 | オーナー | 司令塔 | 調査・制作 | 検収 | 機械ゲート |
|---|---|---|---|---|---|
| 目的・成功条件・KPI | **A/R** | C | C | C | ― |
| タスク分解・割当 | C | **A/R** | C | ― | ― |
| 成果物の作成 | ― | C | **A/R** | ― | C |
| 品質判定 | 例外時A | C | ― | **R** | **R** |
| 不可逆・対外・金銭の行為 | **A/R** | C | ― | C | R（停止） |
| 監査証跡 | C | R | C | C | **A/R** |

A: 最終責任、R: 実行責任、C: 助言。

## 4. 自律度とリスク

### 4.1 自律度レベル（行為の種類ごとに設定する）

| レベル | エージェントに許すこと | 人間の関与 | 例 |
|---|---|---|---|
| **L0 提案** | 読み取り、分析、提案 | 毎回判断 | 戦略案、法務・人事の判断材料 |
| **L1 下書き** | 隔離された作業領域で成果物を作成 | 採用前に確認 | 文書の下書き、コード案 |
| **L2 検証済み実行** | 低リスクの変更を検収後に反映 | 例外だけ確認 | テスト追加、社内レポート |
| **L3 監視付き自律** | 定型範囲を一連で実行し、事後監査 | 対外・不可逆だけ事前承認 | 既知パターンの修正、定例分析 |
| **L4 制限付き全自律** | 狭く、巻き戻し可能で、影響上限が固定された領域で完結 | 抜き取り・事後監査 | 再生成可能な一時環境の保守 |

- `AUT-01`（必須 `[強]`）: 自律度はエージェント単位ではなく**行為の種類ごと**に決め、`policies/autonomy-matrix.md` またはタスクの `autonomy_level` に記録する。
- `AUT-02`（必須 `[強]`）: L4は「何でも任せる」ではない。完全に巻き戻せ、影響の上限が固定された領域に限る。

### 4.2 リスク採点（6軸 × 0〜3点）

| 軸 | 0点 | 3点 |
|---|---|---|
| 可逆性 | 即座に完全に戻せる | 戻せない |
| 外部影響 | 自分の作業領域のみ | 顧客・公開環境・取引先に届く |
| データの機微性 | 公開情報のみ | 個人情報・秘密・認証情報 |
| 金銭・法務・人事 | 関係なし | 支払い・契約・評価・採否 |
| 仕様の曖昧さ | 機械的に合否判定できる | 正解・完了条件が不明 |
| 波及範囲 | 1件で止まる | 連鎖的に広がる |

- `AUT-03`（必須 `[推論]`）: いずれかの軸が3点、または合計10点以上なら、人間の事前承認を必須とする（初期値）。
- `AUT-04`（必須 `[強]`）: エージェントの自己申告の自信度（confidence）を理由にリスク点を下げない。

### 4.3 承認マトリクス

| 行為の種類 | 例 | 単独で可 | 人間の事前承認 | 技術的に遮断 | 実装手段 |
|---|---|---|---|---|---|
| 読み取り・調査 | ファイル閲覧、Web検索、要約 | ✓ | | 秘密情報（`.env`、`secrets/`） | `allow` / `deny: Read(./.env)` |
| 作業領域での作成・編集 | `workspace/` の下書き | ✓ | | | `allow: Edit(/workspace/**)` |
| 共有状態の更新 | `tasks/board.json`、`progress.md` | ✓（司令塔のみ） | | 条件を満たさない done 化 | Stopフック |
| ローカルのコミット | ブランチへの commit | ✓ | | `reset --hard`、force push | `allow` / `deny` |
| リモートへの反映 | `git push`、PR作成 | | ✓ | 保護ブランチ | `ask` |
| **外部への発信** | メール、SNS、動画・記事公開、顧客への返信 | 下書きまで | **✓** | | `ask` ＋ 人手起動スキル |
| **金銭・契約** | 決済、請求、発注、値付け・値引き、契約 | 見積案・比較表まで | **✓** | 会計APIへの書き込み | `deny` |
| **削除・破壊的操作** | 本番データの削除、一括削除 | | ✓ | `rm -rf` 等 | `deny` ＋ PreToolUseフック |
| 権限・設定の変更 | settings、エージェント定義、フック、認証情報 | | ✓（人間が自ら行う） | エージェントによる編集 | `deny` ＋ フック |
| **評価基準の変更** | KPI、受入基準、完了定義、この基準書 | 提案まで | ✓（PRで承認） | エージェントによる編集 | `deny` ＋ フック |
| 新しい外部ツールの導入 | MCP、スキル、依存関係、資格情報 | 提案まで | ✓ | | `ask` |
| スコープ外の新規着手 | 目的に紐づかない新企画 | 提案のみ | ✓ | | 週次計画の承認 |

- `AUT-05`（必須 `[強]`）: 上表の太字の行は、自動化が成熟した後も人間の承認を残す。
- `AUT-06`（推奨 `[推論]`）: 同じ種類の大量処理は、個別承認ではなく「対象の集合・上限・期限・撤回条件」をまとめて一度に承認する（承認疲れの防止）。

## 6. タスク・引き継ぎ・完了の標準

| ID | ルール | 強さ |
|---|---|---|
| `TSK-01` | すべてのタスクはタスクボード（`tasks/board.json`）に登録し、**タスク契約**（`standards/templates/task-contract.yaml`）の必須項目を埋める。 | 必須 `[強]` |
| `TSK-02` | すべてのタスクに `outcome_link`（どの事業成果・KPIに効くか）を書く。**書けないタスクは起票せず、提案として上げる。** | 必須 `[推論]` |
| `TSK-03` | 委任するときは、目的・出力形式・使ってよいツール・作業範囲の境界・完了定義・労力の上限を必ず渡す。 | 必須 `[強]` |
| `TSK-04` | ステータスは `todo` `doing` `review` `blocked` `done` の5値とする。`done` の条件は、`evidence` が1件以上、`verified_by` が検収役またはオーナー、`outcome_link` が記入済みであること。Stopフックで強制する。 | 必須 `[強]` |
| `TSK-05` | エージェント間の受け渡しは、チャットの要約ではなく**引き継ぎ書式**（`standards/templates/handoff.yaml`）のファイルで行う。「問題ありません」「たぶん完了です」だけでは次工程へ進めない。 | 必須 `[強]` |
| `TSK-06` | 司令塔はセッション開始時に `progress.md` の末尾と `tasks/board.json` を読み、終了時に「やったこと／証拠／次の一手／ブロック／成果との関係」を追記する。 | 必須 `[強]` |
| `TSK-07` | 労力の目安を委任時に示す。単純な事実確認は調査役1体・ツール呼び出し3〜10回、比較調査でも最大3体までとする。 | 推奨 `[中]` |

## 7. 会議（エージェント間の協議）の標準

| ID | ルール | 強さ |
|---|---|---|
| `MTG-01` | 会議は「決めるべき問い」と「決定の締切」を一文で書けるときだけ開く。 | 必須 `[推論]` |
| `MTG-02` | 最初の案は**互いに見せずに独立に**作成させる（既定3案）。可能なら情報源・観点・プロンプトを意図的に変える。 | 必須 `[強]` |
| `MTG-03` | 集約は、事前に決めたルーブリックによる採点か多数決で行う。「合意するまで話し合う」ことは禁止する。 | 必須 `[強]` |
| `MTG-04` | 反論（悪魔の代弁者）は1回、全体で2ラウンドまでとする。交換するのは意見ではなく、証拠の欠落の指摘である。 | 必須 `[中]` |
| `MTG-05` | 会議は必ず決定記録（`decisions/YYYY-MM-DD-<slug>.md`）か成果物で終える。決まらなければ、選択肢を2〜3個に絞って例外カードで人間へ上げる。 | 必須 `[推論]` |
| `MTG-06` | 同じモデルの多数決を真実とみなさない。多数決は補助信号にとどめ、外部証拠とルーブリックを優先する。 | 必須 `[強]` |
| `MTG-07` | 常設の雑談部屋や、全エージェントが全メッセージを読む設計は作らない。 | 必須 `[中]` |

会議の種類は次の4つに限る。

| 会議 | 目的 | 出力 | 上限 |
|---|---|---|---|
| キックオフ | 境界・担当・依存関係を確定する | タスク一覧、担当、期限 | 1回 |
| 証拠共有 | 発見と証拠を共有する | 主張と証拠の対応表 | 必要時 |
| 争点裁定 | 矛盾をルーブリックで裁定する | 決定記録 | 2ラウンド |
| ふりかえり | 再発防止策を決める | テスト・フック・ルールの変更案 | 事故時・節目 |

## 8. 検証と品質ゲート

| ID | ルール | 強さ |
|---|---|---|
| `VER-01` | 検収役は作成者と別の文脈で起動し、作成者の推論やメモリを共有しない。受け取るのはタスク契約・成果物・証拠・差分だけとする。 | 必須 `[強]` |
| `VER-02` | 検収は次の順で行う。①成功条件を満たすか、②反例・境界条件で壊れないか、③範囲外の変更がないか、④セキュリティ・プライバシー・権限の違反がないか、⑤証拠が再現できるか。 | 必須 `[強]` |
| `VER-03` | LLMによるレビューより、テスト・型検査・スキーマ検証・リンク確認・実行ログなどの決定的な検査を優先する。 | 必須 `[強]` |
| `VER-04` | 検収の出力は `PASS` / `FAIL` / `INCONCLUSIVE` と根拠に限る。確認できない項目がある場合は PASS にしない。 | 必須 `[中]` |
| `VER-05` | 複数の担当の成果を統合した後は、全体を通した検査をもう一度行う。 | 必須 `[強]` |
| `VER-06` | 検収の見逃しを測るため、オーナーは週に3件、検収済みの成果物を抜き打ちで確認する。 | 推奨 `[推論]` |

## 9. 強制層（権限・サンドボックス・フック）

統制は4層で考える。方針層だけで安全を実現しようとしてはならない。

| 層 | 目的 | Claude Codeでの実装 |
|---|---|---|
| 方針層 | 望ましい行動を教える | `CLAUDE.md`、`.claude/rules/`、スキル、エージェントのプロンプト |
| 権限層 | できる行動を限定する | `permissions` の allow / ask / deny、MCPの限定、資格情報の分離 |
| 実行隔離層 | 誤操作の影響範囲を小さくする | サンドボックス、worktree、ステージング、読み取り専用環境 |
| 検証・監査層 | 失敗を検出し、止め、追跡する | フック、CI、テスト、監査ログ、予算上限 |

| ID | ルール | 強さ |
|---|---|---|
| `ENF-01` | すべてのサブエージェント定義で `tools` を明示する（省略すると全ツールを継承する）。 | 必須 `[強]` |
| `ENF-02` | 保護対象（`kpi/` `acceptance/` `.claude/settings*.json` `.claude/agents/` `.claude/hooks/` `.claude/skills/` `standards/agent-org-standard.md` `.env` `secrets/`）への書き込みを、`deny` と PreToolUseフックの両方で遮断する。`Edit` の deny は Bash 経由の書き込みを防げないため、フックで補う。 | 必須 `[強]` |
| `ENF-03` | `git push --force`、`git reset --hard`、`rm -rf`、会計APIへの書き込みは `deny` にする。`git push`、外部送信系のMCPツールは `ask` にする。 | 必須 `[強]` |
| `ENF-04` | `bypassPermissions` は隔離されたコンテナ・VM以外で使わない。導入初期は `defaultMode: default`、実績が積み上がってから `auto` に移行する。`auto` に移行しても deny とフックは残す。 | 必須 `[強]` |
| `ENF-05` | 副作用のある手順（公開依頼、週次計画など）のスキルは `disable-model-invocation: true` にし、人間だけが起動できるようにする。 | 必須 `[強]` |
| `ENF-06` | ツール実行を監査ログ（`logs/audit.jsonl`）に記録する。秘密情報はログに残さない。 | 推奨 `[強]` |
| `ENF-07` | フックのスクリプト自体も攻撃対象である。入力を検証し、エージェントが書き換えられない場所に置く。 | 必須 `[強]` |
| `ENF-08` | サブエージェントには `maxTurns` を必ず設定する。 | 必須 `[強]` |

実装例（`settings.json`、`guard-protected.sh`、`check-board.sh`）は報告書A §5.8 を参照すること。導入時には `claude --version`、`/doctor`、`/mcp` で現行の仕様とツール名を確認する。

## 10. メモリと外部情報

| ID | ルール | 強さ |
|---|---|---|
| `MEM-01` | 作業中のメモ、検証済みの知識、恒久ルールを分けて保存する。 | 推奨 `[中]` |
| `MEM-02` | エージェント間のメッセージや外部コンテンツを、そのまま永続メモリに入れない。保存する場合は出典・取得日・信頼度・有効期限を付ける。 | 必須 `[強]` |

## 11. 成果指標と「空回り」の防止

### 11.1 ルール

| ID | ルール | 強さ |
|---|---|---|
| `OUT-01` | 各役割に、先行指標（仕事の質）と遅行指標（事業成果）を対で持たせる。 | 必須 `[推論]` |
| `OUT-02` | 代理指標には必ず対になる指標を置く（例: 制作本数 × 採用率・成果指標）。代理指標だけが改善して成果が横ばいなら赤信号とする。 | 必須 `[中]` |
| `OUT-03` | 「自動承認率が高い」「エージェントが自信を示した」「会議で合意した」「タスク完了数が多い」は品質指標にしない。 | 必須 `[強]` |
| `OUT-04` | KPIの目標値と実績は `kpi/` に人間が置き、エージェントは読むだけとする。 | 必須 `[強]` |
| `OUT-05` | 月次レビューで成果に効いていない役割・タスク種別は、縮小または廃止する。エージェントを残すこと自体を目的にしない。 | 必須 `[推論]` |

### 11.2 役割別KPIと完了定義

| 役割 | 完了定義 | 先行KPI | 遅行KPI（事業成果） | 空回り検出 |
|---|---|---|---|---|
| 司令塔 | 計画の全タスクに `outcome_link` と完了定義があり、done は全件検収済み・証拠つき | 検収一発合格率、1タスクあたりコスト | 計画タスクが成果指標に効いた割合 | 完了数は増えたのに成果が横ばい |
| 調査役 | 答えが出典つきで返り、未確認事項が明示されている | 監査で出典を確認できた割合 | 調査が実際の決定に使われた割合 | 調査本数は多いのに採用がない |
| 制作担当 | 受入基準を満たし、検収で合格し、オーナーが大幅な手直しなしで使える | 大幅修正なしの採用率 | 公開物の成果（視聴維持率、申込数、CVR など） | 制作本数だけが増える |
| 検収役 | 全受入基準について合否と根拠を記録 | 見逃し率（抜き打ちで後から見つかった不備） | 公開後の手戻り・訂正件数 | 合格率が100%に張り付く |
| 成果分析役 | 月次で「どの成果がどのタスクで動いたか」を記述 | 報告の期日遵守 | 見直し・廃止の判断に使われた回数 | 報告は出るのに何も変わらない |

### 11.3 赤信号（2週続いたら設計を見直す）

1. 完了タスク数やトークン消費が増えているのに、遅行KPIが横ばい
2. 検収の合格率が100%に張り付く、またはオーナーの修正・コメントが減り続けている（承認の形骸化）
3. 作られた成果物のうち、下流で使われていないものの割合が高い
4. `outcome_link` が「全体的な改善」「認知向上」など検証できない記述になっている
5. エスカレーションがゼロになった（本当に問題がないのか、止まるべき場面で止まっていないのかを監査する）
6. 同じ論点で会議が2回以上開かれている

### 11.4 アンチパターン

| 作ってはいけない構成 | 代わりに |
|---|---|
| 役職を模した多階層、CEOエージェント | 司令塔1体と専門役、手順と道具 |
| 合意するまで話し合う会議 | 独立起案 → 採点・投票 → 決定記録 |
| 複数エージェントが同じ成果物を並行して書く | 書き手は1体 |
| 自己申告の「完了しました」で閉じる | 検収役の判定と外部証拠 |
| KPIやテストをエージェントが編集できる | deny とフックで保護 |
| 全行為を人間が承認する | 不可逆・対外・金銭だけを承認 |
| 「念のため」の大量調査・大量のサブエージェント | 労力の上限と `maxTurns` |
| 目的と紐づかない「改善」「整理」「資料化」 | `outcome_link` が書けないタスクは起票しない |
| プロンプトの「禁止」だけに頼る | 権限・フック・環境の分離 |

## 12. 人間のレビュー周期と昇格・降格

### 12.1 レビュー周期

| 周期 | 所要 | オーナーがすること | エージェント側の準備 |
|---|---|---|---|
| 随時 | 数十秒/件 | 外部発信・金銭・削除の承認（束ねて提示） | 例外カード |
| 毎日 | 約5分 | ダイジェストを読み、承認待ちに答える。問題なければ何もしない | 「承認待ち／ブロック／赤信号／成果の動き」の4項目だけ |
| 毎週 | 約30分 | 次週計画の**意図を承認**する。検収済み成果物3件を抜き打ち確認する。週次リサーチのPRを確認する（第14章） | 計画案、`outcome_link`、監査サンプル、リサーチPR |
| 毎月 | 約60分 | 成果との結びつきをレビューし、効いていない役割を縮小・廃止する。自律度の昇格・降格を決める | 成果分析役の月次レポート |
| 四半期 | 約60分 | 代理指標と成果の相関を見直し、KPIと完了定義を改訂する | 指標の推移データ |

- `REV-01`（推奨 `[推論]`）: ダイジェストや計画の各項目には「これが何につながるか」を一文添え、「〜すべき」ではなく「〜すると○○が進む」と書く（オーナーの働き方に合わせる。`working_style.md` 参照）。

### 12.2 昇格・降格の基準（初期値 `[推論]`）

| 昇格 | 最低観測量 | 品質条件 | 安全条件 | 運用条件 |
|---|---|---|---|---|
| L0→L1 | 20件 | 90%以上が利用可能 | 重大事故0 | 証拠の記録率95%以上 |
| L1→L2 | 50件 | 成功率95%以上 | 重大な不備0 | 自動検査が整っている |
| L2→L3 | 100件 | 成功率97%以上、差し戻し2%未満 | 無承認の高リスク行為0 | 緊急停止の訓練済み |
| L3→L4 | 限定領域で200件 | 成功率99%以上 | 重大事故0、ヒヤリハット是正済み | 完全に可逆、影響上限が固定 |

- `REV-02`（必須 `[中]`）: 昇格は行為の種類ごとに判断する。直近20件の抜き打ち監査で重大な不備が0件であることを最低条件とする。「慣れ」で昇格しない。
- `REV-03`（必須 `[推論]`）: インシデント（誤送信、誤った公開、保護領域への書き込み試行、虚偽の完了報告）が1件でも起きたら、その行為の種類は即座に1段階降格し、原因をフック・受入基準・CLAUDE.mdのいずれかに反映する。
- `REV-04`（必須 `[強]`）: モデル、プロンプト、ツール、MCP、権限、主要な依存関係が変わったら、自律度を再評価する。

## 13. 新しいエージェント・仕組みを作るときのチェックリスト

Claude Codeは、エージェントやスキルを新規作成・変更する前に、次を満たす設計メモ（PR本文でも可）を作成すること。

- [ ] **目的と成果:** どの事業成果（`outcome_link`）に効くかを一文で書いた（`TSK-02`）
- [ ] **構成の選択:** 単一エージェントや固定ワークフローで足りない理由を書いた（`ARC-01` `ARC-02`）
- [ ] **役割:** 標準5役のどれに当たるか、新しい役割ならその理由（`ROL-12`）
- [ ] **書き手:** 成果物の書き手が1体であることを確認した（`PRI-02`）
- [ ] **権限:** `tools` を明示し、最小限にした。`maxTurns` を設定した（`ENF-01` `ENF-08`）
- [ ] **自律度:** 行為の種類ごとの自律度とリスク点を記録した（`AUT-01` `AUT-03`）
- [ ] **承認:** 対外・金銭・削除・設定変更が人間承認または遮断になっている（`AUT-05` `ENF-03`）
- [ ] **検収:** 作成者と別の検収の経路がある（`PRI-03` `VER-01`）
- [ ] **完了定義:** 受入基準があり、done の条件が機械的に検査される（`TSK-04`）
- [ ] **停止条件:** エスカレーション条件と労力の上限を書いた（第5章、`TSK-07`）
- [ ] **KPI:** 先行・遅行・空回り検出の指標を決めた（`OUT-01` `OUT-02`）
- [ ] **巻き戻し:** 失敗時の戻し方と緊急停止の方法を確認した（`ESC-09`）
- [ ] **既存設定との衝突:** 既存の CLAUDE.md、`.claude/settings*`、フック、スキル、エージェント定義を上書きしていない
- [ ] **登録:** `standards/feedback-targets.md` に、このエージェントの所在と担当範囲を追記した（第14章）

最小のサブエージェント定義は `standards/templates/subagent-template.md` を使う。完全な5役のテンプレートは報告書A §5.8 にある。

## 14. 継続的な更新とフィードバック

この分野は変化が速い。本基準書は、週次のリサーチで更新し続ける前提で運用する。

| ID | ルール | 強さ |
|---|---|---|
| `GOV-01` | 毎週1回、定期実行（Claude Code Routines）で新しい論文・公式発表・製品変更を調査し、`standards/research-log/YYYY-MM-DD.md` に記録する。 | 必須 |
| `GOV-02` | 週次リサーチのエージェントは、**提案まで**を担当する（自律度L1）。基準書やエージェント定義の変更は、PRとして提出し、オーナーのマージをもって承認とする。 | 必須 |
| `GOV-03` | 新しい知見は、根拠の強さ（`[強]` `[中]` `[推論]`）と、影響するルールIDを付けて記録する。ベンダーの宣伝、単一の未査読論文、スニペットのみの情報で `[強]` のルールを変えない。 | 必須 |
| `GOV-04` | 影響するエージェントや仕組みは `standards/feedback-targets.md` から特定し、具体的な変更案（差分）を添える。 | 必須 |
| `GOV-05` | 特に重要な変化（Claude Codeの権限・フック・サブエージェント仕様の変更、重大な脆弱性の報告、既存ルールを否定する強い研究）は、PR本文の冒頭に「要判断」として例外カードの形で示す。 | 必須 |
| `GOV-06` | 新しい知見がない週も、「変更なし」としてログを残す。 | 推奨 |
| `GOV-07` | 四半期に一度、週次ログを振り返り、基準書のMINOR/MAJOR改訂を検討する。 | 推奨 |

週次の流れは次のとおりである。

```text
[毎週月曜 朝] Routineが起動
  → 基準書・直近のログ・監視先リスト・フィードバック先を読む
  → 過去7〜10日の新情報を調査（監視先リスト優先）
  → 根拠の強さを評価し、影響するルールIDとエージェントを特定
  → research-log を作成、必要なら基準書・テンプレートの改訂案を作成
  → ブランチにコミットしてPRを作成（要判断事項を冒頭に）
[オーナー] 週次レビュー（約30分）の中でPRを確認し、マージ／修正依頼／却下
```

監視先は `standards/sources-watchlist.md` に、フィードバック先は `standards/feedback-targets.md` に置く。
